# Linux-агент и безопасное применение nftables

Агент работает на Linux от root и запускает штатный `nft` без shell. Контроллер `gfwd` работает отдельным пользователем `gfw` и обращается к агенту через Unix-сокет. Применение включается явно флагом `-enable-apply`. Без него агент только читает интерфейсы, в том числе на macOS.

## LAN и защищённый доступ к панели

Перед запуском задайте фактические LAN-интерфейс и TCP-порт панели. Например, `br-lan` и `8443`. Интерфейс должен существовать, быть включён и не быть loopback. Административный флаг UP проверяется до планирования и применения; наличие carrier и фактическую доступность проверяет администратор после применения.

В управляемой таблице системные правила стоят перед пользовательскими:

- Вход на TCP-порт панели через выбранный LAN разрешён для IPv4 и IPv6.
- Ответы с этого порта в LAN разрешены даже при пользовательском запрете исходящего трафика.
- Служебный ICMPv6 для соседства и ошибок на LAN разрешён в обе стороны.
- Loopback разрешён в обе стороны.

Эти правила не редактируются и не отключаются политикой из браузера. Приоритет защиты доступа выше пользовательского `drop`. Правило не разрешает панель через WAN. Оно не может отменить запрет в чужой таблице nftables, ошибку адресации, остановку HTTPS-службы или иной внешний фильтр. Listener `gfwd` должен действительно слушать LAN на указанном порту: стандартный локальный `127.0.0.1:8088` сам по себе не делает панель доступной из LAN.

LAN-параметры записываются в журнал агента. Изменение этих параметров при существующем журнале блокирует запуск: миграцию интерфейса или порта нужно планировать отдельно с консольным доступом и резервной копией, а не удалять журнал действующего шлюза.

## Применение и подтверждение

1. Сохраните черновик и откройте предпросмотр. При подключённом активном агенте это результат проверки `nft -c -f -` на Linux, включая anti-lockout.
2. Нажмите «Применить сохранённое». Время подтверждения — 30–600 секунд, начальное значение 120. Применяется указанная сохранённая ревизия; конкурирующий новый черновик вызывает ошибку ревизии.
3. Агент снимает только собственную таблицу, проверяет замену, записывает и синхронизирует журнал восстановления, затем одной транзакцией `nft -f -` заменяет `inet gfw`.
4. После успешной установки и чтения таблицы операция переходит в ожидание подтверждения. Проверьте доступ через LAN и нажмите «Доступ работает — подтвердить» до срока. Подтверждение фиксируется на диске.
5. При тайм-ауте агент восстанавливает предыдущую таблицу. Если до первого применения таблицы не было, откат удаляет только созданную GFW таблицу. Кнопка «Вернуть предыдущие правила» выполняет тот же откат немедленно.

Таймер работает в агенте независимо от браузера, `gfwd` и БД контроллера. При штатной остановке агента неподтверждённая операция откатывается. После аварии или перезапуска она откатывается сразу перед открытием API, даже если исходный срок ещё не истёк. Подтверждённые правила восстанавливаются при следующем запуске агента, включая загрузку ОС.

При ошибке восстановления операция остаётся `rollback_failed`, новые применения запрещены, агент повторяет попытку каждую секунду. На этапе запуска неудачное восстановление завершает агент с ошибкой; systemd повторяет запуск. Во время остановленного процесса или выключенной ОС таймер исполняться не может: восстановление происходит после запуска. Для рабочего шлюза служба systemd обязательна.

Таймер проверяется каждую секунду; фактический откат может задержаться на время выполняющегося обращения к ядру. Каждый вызов `nft` ограничен пятью секундами. Ошибка или тайм-аут после возможной записи в ядро считается неопределённым результатом и запускает откат.

Другие таблицы не очищаются. Чужая таблица с именем `inet gfw` без метки `gfw-managed-v1` блокирует работу. Потеря файла журнала при наличии управляемой таблицы также блокирует старт вместо принятия неизвестного состояния за подтверждённое. Не разрешайте другим сервисам параллельно менять `inet gfw`; изменение её содержимого перед подтверждением обнаруживается и вызывает откат.

Журнал `/var/lib/gfw-agent/journal.json` содержит подтверждённую конфигурацию, предыдущий снимок незавершённой операции и последние 100 результатов. Запись выполняется через временный файл, fsync, rename и fsync каталога. Файл `agent.lock` запрещает одновременно запускать два агента с одним каталогом состояния. Идемпотентность ID действует для текущей и последних 100 операций; повтор ID с другим содержимым отклоняется.

## Установка на ALT Linux p10

Пакеты `nftables` и `iproute2` установите из репозитория p10. Бинарники собираются без CGO. Для x86_64:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o bin/linux-amd64/gfw-agent ./cmd/gfw-agent
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o bin/linux-amd64/gfwd ./cmd/gfwd
```

Создайте системную группу и пользователя `gfw`, если их ещё нет. Установите бинарники в `/usr/sbin/`, а unit-файлы из `deploy/systemd/` — в `/etc/systemd/system/`. Создайте `/etc/gfw/agent.env` по `deploy/agent.env.example`, указав существующий LAN-интерфейс и порт 8443. Проверьте путь к `nft` и при необходимости скорректируйте unit.

Пример для новой тестовой установки от root (существующие учётные записи предварительно проверьте):

```sh
groupadd --system gfw
useradd --system --gid gfw --home-dir /var/lib/gfw --shell /sbin/nologin gfw
install -m 0755 bin/linux-amd64/gfw-agent /usr/sbin/gfw-agent
install -m 0755 bin/linux-amd64/gfwd /usr/sbin/gfwd
install -d -m 0750 -o root -g gfw /etc/gfw /etc/gfw/tls
install -m 0640 -o root -g gfw deploy/agent.env.example /etc/gfw/agent.env
install -m 0644 deploy/systemd/gfw-agent.service /etc/systemd/system/gfw-agent.service
install -m 0644 deploy/systemd/gfwd.service /etc/systemd/system/gfwd.service
```

До включения служб отредактируйте `/etc/gfw/agent.env` и установите действующие TLS-сертификат `/etc/gfw/tls/server.crt` и ключ `/etc/gfw/tls/server.key`. Ключ должен быть доступен только root и группе gfw (0640). Unit `gfwd` слушает HTTPS на 8443; дальнейшее управление CA/ACME и сменой сертификата панели доступно в [модуле сертификатов](certificates.md).

```sh
systemctl daemon-reload
systemctl enable --now gfw-agent.service gfwd.service
systemctl status gfw-agent.service gfwd.service
journalctl -u gfw-agent.service -u gfwd.service
```

Каталоги данных и runtime создаёт systemd. Сокет root:gfw имеет 0660 в каталоге 0750; члены группы gfw могут управлять firewall и считаются доверенными администраторами. Состояние агента root:root/gfw с 0700 не доступно контроллеру. Для входа в панель прочитайте созданный `/var/lib/gfw/admin.token` с правами владельца/root. Первый запуск не устанавливает default-drop автоматически: правила появляются только после явного применения.

Не подключайте дополнительную загрузку `inet gfw` через `/etc/nftables.conf`. Если другая служба очищает весь ruleset после старта агента, правила будут потеряны; устраните такого второго владельца. Unit упорядочен после `nftables.service` и сети. До старта агента при загрузке ОС сохранённые правила ещё не установлены: отдельный ранний boot-фильтр в эту итерацию не входит.

## API

Управление VLAN/bridge/bond, IP и маршрутами добавлено отдельным статическим адаптером etcnet с общим подтверждением: [инструкция по сети](network-management.md). Сетевые операции включаются флагом `-enable-network`; обновлённый systemd unit уже включает его. После первого сетевого применения журнал имеет версию 2: старый агент должен отказаться от запуска, поэтому понижение до версии без сетевого восстановления не поддерживается.

Через защищённый API контроллера:

- `POST /api/v1/changes/plan` — конфигурация правил, результат проверки и системное правило LAN.
- `GET /api/v1/changes/state` — срок, статус, подтверждённая ревизия и история агента.
- `POST /api/v1/changes/apply` — `id`, `revision`, `timeout_seconds`; конфигурация берётся из БД, не из тела запроса.
- `POST /api/v1/changes/{id}/confirm` — зафиксировать подтверждение.
- `POST /api/v1/changes/{id}/rollback` — отменить неподтверждённое изменение.

Cookie-запросы требуют CSRF. Намерение применения/подтверждения/ручного отката журналируется в SQLite до обращения к агенту. Автоматические исходы находятся в независимом журнале агента и доступны в UI; их сохранение не зависит от доступности контроллера.

## Проверка

`go test -race ./...` проверяет тайм-аут, границу дедлайна, повтор запросов, одновременные операции, аварийное восстановление, недоступность диска, отказ и повтор отката, изменение live-таблицы и запрет смены LAN. Реальные `nft`, таблицы и сетевой доступ проверяются скриптом `scripts/test-alt-p10.sh` в отдельном контейнере ALT p10 с `--network none`. Контейнеру нужны расширенные сетевые права для создания лабораторных namespace; сеть хоста он не использует. Это проверка userspace ALT p10 на ядре Docker, а не полноценная проверка загрузки ALT p10 с systemd.
