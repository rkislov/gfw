# Руководство администратора GFW

GFW управляет выделенным шлюзом ALT Linux p10/p11 или Ubuntu 26.04 LTS. Пакет содержит контроллер, Linux-агент, веб-панель и команду настройки sysctl. Выберите RPM или DEB для системы и архитектуры шлюза. Подробности установки, обновления и состава пакета приведены в [инструкции по RPM](single-package.md).

## Первый запуск

1. Подготовьте статический адрес на интерфейсе управления LAN. В примере это `br-lan`.
2. Установите RPM и запустите первичную настройку от root.

   ```sh
   # ALT Linux p11 (x86_64)
   apt-get install ./gfw-0.22.4-1.altp11.x86_64.rpm
   # На ALT p10 выберите RPM с суффиксом altp10.
   # Ubuntu 26.04 (amd64)
   # apt install --no-install-recommends ./gfw_0.22.4-1.ubuntu26.04_amd64.deb
   gfw-setup br-lan
   systemctl status gfw-agent gfwd
   ```

3. Откройте `https://<IP-адрес-LAN>:8443` из LAN. Для новой установки войдите с логином `admin` и паролем `admin`. После входа откройте **Пользователи и вход**, выберите `admin` и задайте новый пароль из 12–72 байт. Сохраните ключ из `/var/lib/gfw/admin.token` для аварийного доступа. Установите сертификат панели, которому доверяют браузеры пользователей. [Сертификаты и ACME](certificates.md).
4. В **Межсетевой экран** сохраните и проверьте базовую политику. Примените её, повторно откройте панель из LAN и подтвердите изменение. Системное правило anti-lockout защищает порт управления на указанном LAN. При работе с WAN и VPN разрешайте нужные порты отдельными правилами.

## Дашборд

В разделе **Обзор системы** доступно текущее состояние узла. Графики CPU, памяти и трафика выбранного интерфейса обновляются каждые две секунды. История за последние две минуты собирается в открытой вкладке. Список служб показывает фактическое состояние, а блок **Актуальность IOC** — время последнего успешного обновления, расписание и число индикаторов в локальном снимке Security Feed.

Блок VPN показывает сеансы сервера OpenVPN и установленные SA IKEv2. Вход по сертификату отображается по идентификатору сертификата, если сервер не передал логин. Для WireGuard блок показывает пиры с handshake за последние три минуты.

В **Настроить дашборд** выберите виджеты и измените их порядок стрелками. Настройки сохраняются в этом браузере для текущей учётной записи.

## Изменение сети и политики

На ALT в **Сетевые интерфейсы** задайте физические порты, VLAN, bridge, bond, IP-адреса и маршруты. Подтверждённые настройки сохраняются через etcnet. Проверяйте доступ к LAN, маршруты и разрешение имён после каждого применения. При потере доступа дождитесь таймера отката. [Управление сетью](network-management.md).

На Ubuntu тот же раздел управляет выделенными интерфейсами через Netplan и systemd-networkd. LAN и его зависимости ведёт исходный профиль Ubuntu. Для первой настройки сохраните действующий LAN, выберите отдельные порты для GFW и проверьте план до применения.

Правила межсетевого экрана разделены по направлениям **К устройству**, **Через устройство**, **От устройства**. Первое направление используют, например, для входа к DNS или VPN на самом шлюзе. Второе — для прохода между сетями. Включайте журналирование на нужных правилах и проверяйте порядок. [Правила и применение](firewall-management.md).

| Сертификаты и ACME | Создайте локальный CA для VPN, выпустите серверные и клиентские сертификаты, настройте ACME для публичных имён. [Управление сертификатами](certificates.md) |

## Учётные записи и источники паролей

В **Пользователи и вход** создайте запись с логином из строчных латинских букв, цифр, точки, дефиса и подчёркивания. Первый символ — буква, длина до 63 символов. Роль **Пользователь VPN** даёт доступ к личному кабинету. **Администратор** получает право менять шлюз. Источник пароля определяется при создании записи.

- **Локальная база.** Задайте пароль длиной от 12 до 72 байт. Оставьте поле пустым при редактировании, чтобы сохранить текущий пароль.
- **LDAP.** Укажите адрес `ldaps://directory.example.org:636`, Base DN и атрибут логина, например `uid` или `sAMAccountName`. При необходимости добавьте Bind DN и пароль сервисной записи с правом поиска. Для внутреннего PKI добавьте сертификат CA в PEM. GFW проверяет имя и доверие TLS, ищет ровно одну запись и проверяет пароль входом от её имени.
- **RADIUS.** Укажите `сервер:1812` и общий секрет длиной от 16 до 256 байт. На стороне RADIUS добавьте шлюз GFW как клиента по его исходному адресу. GFW отправляет PAP Access-Request с NAS-Identifier `gfw` и требует подписанный Access-Accept с Message-Authenticator. Используйте выделенную сеть управления или защищённый транспорт между шлюзом и RADIUS. Схема принимает или отклоняет пароль одним запросом. Второй фактор проверяет GFW.

Создайте в GFW явную запись для каждого LDAP- и RADIUS-пользователя, которому нужен доступ. Назначайте роль и VPN отдельно. При входе в панель настроенный пользователем TOTP обязателен. В VPN требование TOTP задаётся у слушателя. При потере приложения убедитесь в личности пользователя и сохраните запись с флажком **Сбросить 2FA**.

Блокировка записи прекращает вход и выдачу профилей, а также новые проверки учётных данных OpenVPN и IKEv2 через брокер. Токен уже открытого сеанса OpenVPN используется для обновления ключей до восьми часов. Для немедленного отзыва действующих VPN-сеансов дополнительно завершите их на шлюзе. При сертификатном доступе отзовите клиентский сертификат, а для WireGuard выключите или удалите peer и примените изменение.

## Выдача личных профилей VPN

Сначала примените и подтвердите конфигурацию VPN. Затем откройте учётную запись и добавьте профиль из списка подтверждённых. Пользователь получит файл из **Личный кабинет → Мои подключения VPN**. Для доступа к кабинету дайте пользователю защищённый маршрут до панели. LAN anti-lockout не открывает кабинет на WAN.

### OpenVPN

1. В **VPN → OpenVPN** создайте управляемый сервер. Укажите TUN, адрес сети, транспорт, порт и серверный сертификат локального CA. Для экспорта укажите публичное имя или IPv4 и маршруты клиента.
2. Выберите источник пароля, клиентский сертификат и TOTP по требуемой политике. Вариант **Локальная база или LDAP** принимает пароль из источника, назначенного каждой конкретной записи. В сертификатном режиме CN сертификата клиента, которому указан логин, должен совпадать с ним.
3. Добавьте допуск клиента с логином и постоянным IPv4. При сертификатном доступе выберите его клиентский сертификат. Настройте правила доступа к слушателю и из VPN, затем подтвердите конфигурацию.
4. Назначьте сервер записи. Проверьте подключение клиентом OpenVPN 2.6+ и при необходимости журнал экземпляра. Режим управляемого исходящего клиента использует сертификаты. [OpenVPN](openvpn.md).

### WireGuard

Создайте туннель и peer, сгенерируйте персональный ключ peer на агенте и заполните публичный endpoint туннеля, клиентский адрес и маршруты. Примените, подтвердите и назначьте этот peer одному пользователю. Личный кабинет контролирует выдачу файла. Сам туннель использует ключ WireGuard. [WireGuard](wireguard.md).

### IPsec / IKEv2

Выберите **VPN → IPsec / IKEv2 → Удалённый доступ IKEv2**. Укажите локальный IPv4 шлюза, публичное имя из SAN серверного сертификата, локальные подсети и отдельный IPv4-пул /16–/30. Настройте пароль и при необходимости TOTP. Для сочетания с клиентским сертификатом укажите логин владельца и сертификат с этим логином в DNS SAN. Клиенту нужен IKEv2 с EAP-GTC. Комбинация сертификата с EAP требует поддержки нескольких раундов аутентификации.

Откройте UDP 500/4500 на соответствующем входе. Проверьте маршруты, примените и подтвердите конфигурацию, затем назначьте профиль. Один шлюз поддерживает один активный профиль удалённого доступа. strongSwan передаёт проверку EAP-GTC локальному брокеру GFW через RADIUS на loopback `127.0.0.1:18128`. Секрет между службами хранится в `/etc/gfw/vpn-auth.key`. Для туннелей между шлюзами действует отдельный режим взаимной аутентификации сертификатами. [IPsec](ipsec.md). [Поддержка EAP-GTC в strongSwan](https://docs.strongswan.org/docs/6.0/plugins/eap-gtc.html).

## Производительность (sysctl)

Откройте **Производительность (sysctl)** и выберите **Обновить расчёт**. Панель покажет доступные логические CPU, RAM и текущие и предлагаемые значения:

- `net.core.somaxconn` — предел очереди ожидающих соединений для TCP-слушателей.
- `net.core.netdev_max_backlog` — предел очереди входящих пакетов при отставании обработки.
- `net.netfilter.nf_conntrack_max` — предел количества отслеживаемых соединений. Расчёт использует бюджет до 1/32 RAM при ориентире 1 КиБ на запись и верхний предел 1 048 576. Реальный расход зависит от ядра и расширений conntrack.

Профиль повышает лимиты до рассчитанных значений и сохраняет уже установленные более высокие лимиты. Недоступные ключи отображаются отдельно. Применение в панели блокируется, пока на агенте ожидает подтверждения другое изменение. Маршруты, forwarding, nftables, IPS и LAN anti-lockout управляются в своих разделах. [Сетевые параметры Linux](https://docs.kernel.org/admin-guide/sysctl/net.html). [Параметры conntrack](https://docs.kernel.org/networking/nf_conntrack-sysctl.html).

Нажмите **Применить профиль** после просмотра. Изменения вступают в силу сразу и сохраняются в `/etc/sysctl.d/80-gfw-performance.conf`. При ошибке записи GFW пытается восстановить исходные значения. Кнопка **Восстановить прежние значения** возвращает исходные значения и удаляет файл профиля. Чтобы пересчитать активный профиль после изменения ресурсов, сначала восстановите исходные значения. При настройке хоста вручную проверяйте другие файлы sysctl.d на конфликт.

Те же операции из root-консоли:

```sh
gfw-sysctl plan
gfw-sysctl apply
gfw-sysctl restore
```

Восстановление ждёт снижения нагрузки, если текущая занятость conntrack достигла исходного лимита. Сравнивайте под одинаковой нагрузкой drops в `/proc/net/softnet_stat`, число записей и счётчики переполнения conntrack, использование RAM, задержку и пропускную способность. Повышение лимитов ориентировано на перегрузку очередей и ёмкость таблицы. Эффект зависит от нагрузки.

## Обслуживание

Перед обновлением остановите обе службы и сохраните `/etc/gfw`, `/etc/sysctl.d/80-gfw-performance.conf`, если он существует, `/var/lib/gfw` и `/var/lib/gfw-agent`. Храните копию закрытой, вместе с ключами хранилищ и SQLite. Для ClickHouse и etcnet используйте отдельные копии.

При сбое проверьте `journalctl -u gfwd -u gfw-agent`, раздел **Аудит изменений**, статус подтверждённой ревизии и журнал конкретного сервиса. Проверяйте сетевой доступ к LDAP/RADIUS, сертификат LDAPS, настройку RADIUS-клиента и синхронизацию времени при проблемах входа. Для доступа к панели через LAN сверяйте имя интерфейса и порт управления с настройками агента.
